## 1. Scope

This lock covers all existing GANDOM implementations and their dependencies:
- Mother law, governance, contracts, and change control
- Core runtime, engines, APIs, and service lifecycle
- Brain, neurons, memory, AI engines, and task execution
- Live nodes, peer discovery, P2P identity, messaging, and recovery
- Cellular mechanisms, software organs, and inter-component interfaces
- DNA/software rules, versioning, and reproducibility
- Security, authentication, authorization, and threat management
- Data, storage, images, evidence provenance, and integrity
- Mathematics, geometry, functions, derivatives, and physics implementations
- Servers, infrastructure, monitoring, and incident recovery
- User interface, market, wallet, Android APK, and installation
- GitHub workflows, build artifacts, tests, and release processes
- Existing backups, history, and discovered useful capabilities

This list defines the audit scope; it does not assert that every capability
already exists, is connected, or has passed real-world verification.

## 2. Immutable acceptance rules

1. Never claim PASS_REAL without actual execution, measurable output,
   retained evidence, and independent verification.
2. Treat unverified functionality as UNVERIFIED.
3. Do not delete or replace existing files before checking dependencies,
   proving the proposed change safe, and preserving a rollback path.
4. Avoid duplicate backups, duplicate reports, and parallel implementations.
5. Preserve existing running services unless a justified change is approved.
6. Validate identity, authorization, input, and failure handling at trust
   boundaries, according to the component's threat model.
7. Record useful findings in the relevant live subsystem when integration
   is verified; a report alone is not evidence of integration.
8. Make changes traceable and reversible.
9. Reuse existing valid evidence where applicable; do not repeat tests
   without a technical reason or when the implementation has not changed.
10. Do not treat a successful workflow, file, process, or local-only test
    as proof that the entire distributed system works.

## 3. Required acceptance chain

CONTRACT
-> REAL_CODE
-> DEPENDENCIES
-> REAL_EXECUTION
-> MEASURABLE_OUTPUT
-> EVIDENCE
-> INDEPENDENT_VERIFICATION
-> PASS_REAL

If any required stage is missing, the affected capability remains UNVERIFIED.

## 4. Integration procedure

A. Discover existing components and evidence before changing them.
B. Map dependencies, duplicate implementations, and missing interfaces.
C. Preserve working code and running services.
D. Integrate only after reviewing conflicts and rollback options.
E. Run targeted real tests for changed behavior.
F. Verify outputs independently and record the evidence location.
G. Report exact PASS, FAIL, and UNVERIFIED status per component.

## 5. Security requirements

Assess node identity, peer authentication, transport protection, access
control, secrets handling, input validation, rate limiting, data integrity,
image provenance, dependency risk, audit logging, recovery, and release
integrity. Use risk-based tests and independent review. No claim of absolute
or globally guaranteed security is permitted.

## 6. Change-control boundary

This document registers the unified acceptance specification only.
It does not modify the canonical mother law, grant PASS_REAL to any component,
prove runtime integration, or authorize destructive cleanup.
